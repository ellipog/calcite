| D16 | 2026-10-26 | Plugin instances | One instance per region plus one global instance per plugin, talking by messages | Phase 0 |
| D17 | 2026-10-26 | WASM runtime | Embed Wasmtime (Apache 2.0). A custom WASM-to-C compiler is an option after Phase 8 | Phase 7 |
| D18 | 2026-10-26 | Goals and tie-breaks | Three goals: plugin development, performance, vanilla parity (bugs excepted). Parity wins wherever players, farms or data packs could observe the difference. Performance wins wherever nothing is observable. The plugin API never forces a parity or performance compromise in core | Phase 0 |
| D19 | 2026-10-26 | Tick model | Lockstep: every region finishes tick N before any region starts tick N+1. Regions are tasks on a work-stealing pool with more regions than threads. Why: it's the only model that keeps results identical across thread counts and gives world-wide operations vanilla's semantics. Cost: the heaviest region sets the tick time. Mitigated by splitting hot regions and moving parallel work (lighting, pathfinding, worldgen, packet encoding) off the region's critical path | Phase 0 |
| D20 | 2026-10-26 | Tick phases | Each tick runs a global phase (central world actor with exclusive access to the whole world), then the region phase (all regions in parallel), then message exchange (delivery ordered by sender region ID, then send sequence). Anything that can reach beyond one region runs in the global phase: unbounded selectors, data pack functions, sleeping, world-wide spawners, raids, world border, dragon fight. The exact order within a tick is settled in `CALX_SPEC.md` and judged by the rig | Phase 0 |
| D21 | 2026-10-26 | Determinism contract | The same tick-indexed input log gives the same output with any thread count. Inputs are packets (tagged with the tick that handles them), finished chunk loads and generations, console input, and results of plugin I/O. Calcite can record the log and replay it from Phase 4 on. This is what "one thread or many, same answer" means | Phase 0 |
| D22 | 2026-10-26 | Region layout | Region split and merge decisions are a pure function of world state at the tick barrier. Region IDs are assigned deterministically | Phase 5 |
| D23 | 2026-10-26 | Memory safety | Calx is memory-safe by default: bounds checks (elided when the compiler can prove them), no null (optional types instead), and no pointer arithmetic or unchecked casts outside `unsafe`. Only Calcite core and trusted plugins may use `unsafe` and `extern`. Why: without this, the plugin trust boundary (D15) is fake, because an untrusted plugin could corrupt the server without touching `extern` | Phase 0 |
| D24 | 2026-10-26 | References to game objects | Entities, players, chunks and block entities are referred to by generational handles checked on use, not pointers. A stale handle (the entity died or left the region) gives an error the caller must handle | Phase 0 |
| D25 | 2026-10-26 | Panics | A panic in a plugin instance stops that instance while its region keeps ticking. A plugin that keeps panicking is disabled. A panic in Calcite core writes a crash report, then saves and stops, the way vanilla does on a crash | Phase 0 |
| D26 | 2026-10-26 | Generics and modules | Calx has generics and interfaces from v0, monomorphized into C. Each module compiles to its own C translation unit, so builds are separate and incremental. The emitter adds `restrict` wherever ownership proves there's no aliasing, which closes Rust's main codegen advantage over C | Phase 0 |
| D27 | 2026-10-26 | Java-compatible collections | Calx's standard library includes Java-compatible `HashMap`, `HashSet` and `LinkedHashMap`, plus fastutil-compatible open hash collections. Calcite uses them wherever vanilla's iteration order is observable, for example the `HashSet<BlockPos>` behind locational redstone, and fast native collections everywhere else. Where vanilla iterates identity-hashed collections, its order isn't reproducible, so Calcite uses a fixed order and lists it as a deliberate difference | Phase 0 |
| D28 | 2026-10-26 | Strings | Calx strings are UTF-8 internally. The standard library provides Java's `String.hashCode` (over UTF-16 code units), UTF-16 length for protocol limits, and a Modified UTF-8 codec for NBT | Phase 0 |
| D29 | 2026-10-26 | Worldgen determinism | Worldgen output is a pure function of seed, data packs and chunk position, whatever the generation order or thread count. Features are decorated in a fixed order: chunks are colored by (x mod 3, z mod 3), and each color class is decorated in turn. Chunks in one class are 3 apart, so their 3×3 write areas never overlap. The rig drives vanilla in the same order. Vanilla's order- and path-dependent bugs (MC-55596, MC-272481, MC-241546) are listed as deliberate differences | Phase 5 |
| D30 | 2026-10-26 | Vanilla content | Neither repo nor any Calcite release contains Mojang content. The build and the first run download the official server jar from Mojang, checked against the SHA-1 in Mojang's version manifest, and Calcite reads the built-in data pack and structure templates from it. A local jar can be supplied instead | Phase 2 |
| D31 | 2026-10-26 | World format | Calcite reads and writes only its own version's world format and has no data fixers. Older worlds are upgraded by opening them in vanilla first. On a version bump, Calcite's worlds are upgraded the same way, which works because worlds round-trip | Phase 5 |
| D32 | 2026-10-26 | Native libraries | libdeflate (MIT) for zlib and deflate, lz4 (BSD-2) for vanilla's LZ4 region-file option, and one vendored crypto library, chosen in Phase 3, that covers AES with AES-NI, RSA PKCS#1 v1.5, SHA-1, SHA-256, HMAC-SHA256, MD5 and a TLS 1.3 client. AES-CFB8 is written directly on the AES block function | Phase 3 |
| D33 | 2026-10-26 | Networking | Event-driven I/O: IOCP on Windows, epoll on Linux. Connections live in a network layer that routes packets to the region owning each player. Packet encoding, compression and encryption run off the region threads, and regions never block on I/O | Phase 3 |
| D34 | 2026-10-26 | Performance tracking | Performance is tracked from Phase 3, not just measured in Phase 8. The tick-loop benchmark comes first, then a fixed bot scenario from Phase 4. Results go in the repo per commit, and a regression over 5% gets investigated before more work lands. CI runners are too noisy to gate on, so the numbers come from one fixed machine | Phase 3 |
| D35 | 2026-10-26 | Host API stability | The host API follows semver. A plugin built against major version N loads on any Calcite with the same major version, native or WASM. Breaking changes need a major bump and a deprecation cycle | Phase 7 |
| D36 | 2026-10-26 | Plugin data storage | Plugin persistent data lives in Calcite's own files next to the world, keyed by UUID, handle or position, so vanilla round trips never lose it. Data that must travel with an item or entity uses vanilla's `custom_data` component | Phase 7 |
| D37 | 2026-10-26 | Phase 3 gate failure | A mismatched RNG probe is a bug, and it gets fixed. If the benchmark is more than 10% slower than Rust, hand-write the same loop in C. If hand-written C is also slow, fix the benchmark or the compiler flags. If it's fast, the gap comes from Calx semantics, and the semantics change (for example, unchecked indexing in core modules) before any Calcite code is written. Rethinking means changing Calx, not replacing it | Phase 3 |
| D38 | 2026-10-26 | Repo layout | Two repos side by side: `calx` (language, compiler, runtime, standard library) and `calcite` (server, plugins, rig). Calcite's build finds the compiler at `../calx`, overridable with `CALX_HOME`, and from Phase 3 records the calx commit it was tested with | Phase 0 |
| D39 | 2026-10-26 | Line endings | LF everywhere via `.gitattributes`, so case-file hashes are the same on Windows and Linux | Phase 1 |
| D40 | 2026-10-26 | Docs as you go | Docs are written in the same change as the feature, never after. Calx docs live in `calx/docs/` as Markdown: one topic per page, front matter with `title` and `description`, relative links, and page order set in `docs/README.md`. That's enough for any common site generator (Starlight, VitePress, mdBook) to build the docs website later. Each feature lives in exactly one place: `CALX_SPEC.md` while it's designed but not built, then its page in `docs/reference/` once it ships, and that page becomes the normative text | Phase 0 |
| D41 | 2026-10-26 | Tested docs | From Phase 3, every code example in the Calx docs is extracted and compiled by the compiler test suite, and run where it shows output. An example meant to fail is marked with the error it should produce. From Phase 7, host API reference docs are generated from doc comments in the host API definition, and a function without one fails the build | Phase 3 |
