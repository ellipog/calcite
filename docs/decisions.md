| D60 | 2026-10-27 | Floating-point reference and `std.math` | Supersedes D58's method. `std.math` ports fdlibm, with its notice kept (D59), so it gives `StrictMath`'s results bit for bit. Matching that would mean copying HotSpot's GPL stubs, which D59 rules out. The rig records both configurations and reports where they differ, so the cost is measured | Phase 1 |
| D61 | 2026-10-27 | Compiled-in tables and startup data | Calcite compiles in what vanilla defines in code, from the converted data generator reports: block states, the built-in registries and their IDs, item default components, packet IDs, the command tree, and the code-defined biome parameter lists. Codegen makes them constant arrays, so a lookup is arithmetic and an array read with nothing parsed at startup. What vanilla's built-in data pack holds (data-driven registries such as biomes, dimension types and damage types, worldgen settings, tags, loot tables, recipes, advancements, structure templates) Calcite loads at startup from the jar, through the same loader user data packs use, so packs can override it as in vanilla. This reads D30's "Mojang content" as Mojang's code, assets and data pack files. The compiled-in tables are the identifiers, IDs and default values the protocol and save format need, which every compatible server has to encode. Why: the code-defined set is fixed per version, so compiling it in is fastest; the data pack set has to stay overridable | Phase 2 |
| D62 | 2026-10-27 | Pinned server jars | `oracle/versions.json` pins each game version's server jar: URL, size and SHA-1, taken from Mojang's version manifest (with the metadata's own SHA-1 checked) when the version is added. Builds check the local jar against the pin offline and download only when it's missing or wrong. Refines D30's check against the manifest: the manifest is read once, when pinning. Why: builds work offline, every checkout uses the same bytes, and a change upstream can't silently change the jar | Phase 2 |
| D63 | 2026-10-27 | Strict types | Calx's checker is stricter than Rust's, and every rule is an error with no flag to relax it (warnings exist only for deprecation). `T(x)` converts only when every value of `x`'s type is exactly a `T`. Lossy conversions say what they do: `T.wrap(x)` keeps the low bits (Java's narrowing casts), `i32.saturate(f)` and `i64.saturate(f)` are Java's float-to-integer casts, `T.nearest(x)` rounds to a float, and `T.try_from(x)` returns `T?`. `usize` is judged at both its widths. Optionals are built with `some(x)`, never implicitly. A literal must fit its type, hex included. An expression statement must be unit (discard with `_ = f()`). Unused locals, parameters, imports and private items are errors, as are a `var` never reassigned, a `mut` parameter never mutated, unreachable code and shadowing. `and` with `or`, mixed bitwise operators, shifts with `+` or `-`, and `??` with other operators need parentheses. A constant shift count must be under the type's width, and comparing with a NaN constant is an error. Why: Calcite ports Java, where silent conversions and precedence slips are where bit-exactness breaks; catching them at compile time is cheaper than finding them with the rig | Phase 3 |
| D64 | 2026-10-27 | Build speed | Building and running Calx code must be fast, unlike Rust. The front end (lexing, parsing, checking, emitting C) is written for throughput: arena allocation, interned names, no per-node heap work, and no whole-program analysis beyond what monomorphization needs. Each module is its own C file, and clang compiles only C whose text changed, in parallel, from a cache keyed by the C text, flags and compiler version. The runtime is compiled once per target and mode. Debug builds use `-O0` with line tables, and both platforms link with lld. `calx run` reuses the last executable when nothing changed. Build time is tracked like run time (D34), with a generated large program as its benchmark. When the two conflict, run time wins in release builds and build time wins in debug builds | Phase 3 |
| D65 | 2026-10-27 | Editor support | Starts in Phase 3 instead of waiting for the language server (P9.2). The VS Code extension in `calx/tools/vscode` has a TextMate grammar (also used for ```calx blocks in Markdown) and shows errors as you type by piping the editor's text to `calx check --json --stdin`, which prints one JSON diagnostic per line with 0-based lines and UTF-16 columns, as the Language Server Protocol counts them. That format is stable: the test suite checks it matches the text form on every error test. The language server replaces the extension's check runner and reuses the format. Why: `calx check` takes milliseconds, so checking on each change costs nothing, and seeing D63's errors while typing makes the strict checker pleasant to use | Phase 3 |
| D66 | 2026-10-27 | Enums | Calx enums are sum types: a variant holds nothing, values by position, or named fields, and `match` is the only way to read its data. Only an enum without data may name an integer representation (`enum Flag: u8 { OnGround = 1 }`), with values counting up from the previous one. It converts to a number as its representation would, exactly, and back with `Flag.try_from(n)`, which takes the representation's type and returns `Flag?`. Without one, the tag is the smallest of `u8`, `u16` and `u32` that fits and has no number a program can see. Data-less enums compare with `==` and print their variant's name; enums with data do neither until derived `Equal` and `Display` exist. Why: protocol and save-format enums need fixed values, and a tagged union laid out as C would lay it out costs nothing to match on | Phase 3 |
| D67 | 2026-10-27 | Optionals | `T?` is a `T` followed by a `bool`, with no allocation. Optionals don't nest: `T??` doesn't parse and `some(some(x))` doesn't check, so `?.` on an optional field gives that field's optional unchanged. `a ?? b` runs `b` only when `a` is `none`; with a `T?` on the right it gives a `T?`, so `??` chains. `==` compares two optionals element-wise, with IEEE rules inside. `opt!` panics on `none`. The `checked_` methods return `T?`: `MIN.checked_div(-1)` is `none`, since the quotient doesn't fit, but `MIN.checked_rem(-1)` is `some(0)`, which is what Java's `%` gives. Why: no nesting makes field chains and `??` simple, and nested optionals were never needed in the samples or sketches | Phase 3 |
| D68 | 2026-10-27 | Patterns and match | A `match` must cover every value and every arm must be able to match, checked with Maranget's usefulness algorithm, with integer ranges split into intervals (a `rune` excludes surrogates). The error shows a missing value. A guarded arm covers nothing. A capitalized name in a pattern is a variant or constant, never a binding, so a misspelled variant is an error instead of a catch-all as in Rust. Variant patterns may leave out the enum's name, since the input's type says which enum it is. Record patterns name every field or end in `..`. Floats can't be patterns. Patterns bind copies, so there's no `mut` binding. Or-patterns can't bind names yet. `let` takes a pattern that always matches, `let ... else` and `if let` one that might not, and on an optional both match the value inside. An arm body may be `return`, `break`, `continue` or an assignment. A `match` compiles to a chain of tests whose last arm is never tested. Why: exhaustiveness is how a new variant finds every place that must handle it, which matters when porting vanilla's large enums | Phase 3 |
| D69 | 2026-10-27 | Print evaluation order | `print`, `println`, `assert` and `panic` evaluate every interpolation, left to right, before writing anything, as Java builds the whole string before printing it. A function called inside `{...}` that prints therefore writes first. Why: printing piece by piece interleaved output differently from Java, which the rig would flag as a difference | Phase 3 |
| D70 | 2026-10-27 | Generics | Generic functions, structs and enums are checked once, where they're written, against their parameters' bounds only. Each use with real types makes a copy: the body is cloned and checked again with those types, so the emitter only ever sees ordinary code, and every generic call is a direct call clang can inline. A definition with errors has them reported once, and its copies aren't checked; an error that only some types have carries a note naming the use. Copies nest at most 64 deep, which catches a function calling itself with ever bigger types. Unused generic parameters, and impl parameters missing from the impl's type, are errors. This refines D67: through a parameter, optionals nest (`T?` with `T` being `i32?`), and `none` on the right of `??` on such a value is the inner optional, so `r ?? none` takes one level off. Written out, `i32??` still doesn't parse. C names list the types: `choose__i64`, `Pair_i32_str`. Why: Calcite's hot paths need generic code at hand-written speed, and checking at the definition reports an error once, where it is, instead of at every use as C++ templates do | Phase 3 |
| D71 | 2026-10-27 | Generic arguments and inference | In an expression, `<` right after a name with no space starts its generic arguments: `choose<i64>(...)`, `Pair<i32, str>.of(...)`. With a space it's less-than, and `f <T>(x)` gets an error saying to remove the space. A call works its parameters out from, in order: written arguments, the receiver, the arguments left to right with untyped literals (`1`, `none`) waiting for the others, and the expected result type. A parameter still unknown is an error, never a default. Why: the space rule avoids Rust's `::<>` while keeping `a < b` unambiguous, and letting literals wait means `choose(c, 1, 2i64)` picks `i64` instead of failing on `i32` | Phase 3 |
| D72 | 2026-10-27 | Interfaces | An interface holds methods, static functions, typed constants and default methods, with `Self` for the implementing type. An impl matches the interface exactly, parameter names included, since calls can name their arguments, and holds nothing else; its missing members are listed in one error. Because the interface fixes the names, an impl member's unused parameter isn't an error. Structs, enums and primitive types can implement interfaces, each at most once, and overlapping generic impls are errors. A private interface's impl for a private type that's never used is an error. A method is looked up in the type's own impls before its interfaces', and a name two interfaces share needs `Iface.method(x)`. An interface constant is a constant in every copy, so `T.sides` can be a field's default. Calls are direct and constants are inlined. Impl functions' C names include the interface, as in `Lift__Up__go`. `dyn`, associated types, generic interfaces, generic functions in interfaces, defaults for interface constants and the operator interfaces come later. Why: exact conformance is the strict choice (D63), and naming the interface in C keeps profiles readable | Phase 3 |
| D73 | 2026-10-27 | Modules and imports | A file is a module, and module `a.b.c` is `a/b/c.calx` under the source root. The root is the main file's folder, or, when the main file has a `module` line, the folder its parts lead back to. A file in a folder must start with its `module` line, matching its place, so any file checked alone, as editors do, finds the root; a file at the root can leave it out. Names match exactly, case included, on every system. Imports are `import a.b.{X, Y}` only: bare `import a.b` is an error until qualified access (`b.f()`) exists.
