# Oracle rig

The rig runs the same inputs through vanilla and through Calcite and compares the results bit for bit (Phase 1). Vanilla's results are recorded once, as goldens, and their hashes are committed. Calcite is scored against those hashes on every change.

| Part | Where | What it does |
| --- | --- | --- |
| Protocol | [`PROTOCOL.md`](PROTOCOL.md) | The wire format between the runner and an adapter, and every probe's signature |
| Runner | [`runner/`](runner/) | Python: loads cases, runs adapters, records, self-checks, scores |
| Vanilla adapter | [`../oracle/vanilla-adapter/`](../oracle/vanilla-adapter/) | Java 25: runs probes against Mojang's server code |
| Calcite adapter | [`calcite-adapter/`](calcite-adapter/) | Runs probes against Calcite's own code, built from [`../src/rig/`](../src/rig/) with calx |
| Cases | [`../cases/`](../cases/) | Committed inputs, one folder per probe |
| Expected hashes | `../expected/26.3/` | Committed: the hash of vanilla's result for every case, and the quarantine list |
| Goldens | `../golden/26.3/` | Gitignored: vanilla's full results, for `diff` |
| Differences | [`differences/`](differences/) | The registry of places Calcite deliberately differs |
| Math comparison | [`runner/mathcmp.py`](runner/mathcmp.py) | `Math` against `StrictMath` on large sweeps (`P1.5`) |
| Protocol suites | [`runner/sessions.py`](runner/sessions.py) | The protocol bot against vanilla and Calcite, packet by packet (`P4.8`) |
| Light timing | [`runner/light_timing.py`](runner/light_timing.py) | Calcite's light engines timed against vanilla's through the `light` probe ([D182](../docs/decisions.md)) |
| The round trip | [`runner/roundtrip.py`](runner/roundtrip.py) | A world vanilla made, loaded and saved by Calcite, then read by vanilla (`G5.2`) |
| Worldgen with packs | [`runner/terragen.py`](runner/terragen.py) | Chunks Calcite generates with Terralith and Terratonic against vanilla's, block by block (CAL-92) |
| A chunk as it starts to tick | [`runner/ticking.py`](runner/ticking.py) | The chunks a saved world left to post-process, and the rings it left part-way, as each server sends them once they tick, with the blocks set after, block by block ([D329](../docs/decisions.md), [D333](../docs/decisions.md), [D334](../docs/decisions.md), [D337](../docs/decisions.md)) |
| A real client | [`runner/realclient.py`](runner/realclient.py) | Mojang's 26.3 client joins Calcite, walks and chats (`G4.1`), goes to another dimension, and times the chunks it's sent through [`runner/chunkwatch.py`](runner/chunkwatch.py) |
| The lockstep check | [`lockstep.py`](lockstep.py) | A session Calcite records on many threads, replayed on one to the same packets and lines (`G5.3`, [D283](../docs/decisions.md)) |

The runner needs only Python 3.10 or newer, with no packages. Run it from anywhere. Paths are relative to the repo.

## Vanilla's two configurations

At the last bit, "vanilla" depends on the JVM. On x86-64, HotSpot replaces `Math.sin`, `cos`, `tan`, `pow`, `log`, `log10`, `exp`, `cbrt` and `tanh` with intrinsics. Those differ from `StrictMath` by 1 or 2 ULP on up to 10% of inputs, so the same seed can give slightly different numbers. Matching the intrinsics would mean copying HotSpot's code, which is GPL and so can't go in an MIT project (D59). So the rig records vanilla two ways (D60):

| Configuration | JVM flags | Role |
| --- | --- | --- |
| `strict-math` | `-XX:+UnlockDiagnosticVMOptions -XX:-UseLibmIntrinsic` | **The reference.** `Math` gives exactly `StrictMath`'s results, which Calx's `std.java.math` can match. Hashes in `expected/26.3/` |
| `intrinsics` | HotSpot's defaults | What most servers run. Hashes in `expected/26.3/intrinsics/` |

Calcite is scored against `strict-math`. The scoreboard also says how many cases Calcite would pass against `intrinsics`, and `list` shows how many cases come out differently in the two. That gap is the measured cost of not copying. In 26.3 it shows up in `math` (30 cases), `rng` (17, every one using `nextGaussian`, which calls `Math.log`) and `mth` (2: `Mth.atan2`, whose table is built with `Math.cos`).

Both configurations repeat bit for bit under every self-check variant, on Windows (Temurin 25.0.5) and on Linux (Ubuntu's OpenJDK 25.0.4), and the two platforms give the same hashes.

## Commands

```sh
py -I rig/runner/rig.py list                     # cases per probe, recorded, quarantined
py -I rig/runner/rig.py record --config all      # run vanilla; write goldens and expected hashes
py -I rig/runner/rig.py check --variants all     # the self-check
py -I rig/runner/rig.py score                    # score Calcite
py -I rig/runner/rig.py diff rng legacy-seed-0   # one case, Calcite's result against vanilla's golden
py -I rig/runner/rig.py orders                   # whether vanilla's decorations depend on their order
py -I rig/runner/mathcmp.py                      # Math against StrictMath, 500,000 arguments per range
```

Every command takes `--probe NAME` (repeatable) to limit it to some probes. `record` and `check` take `--config strict-math` (the default), `intrinsics` or `all`. On Linux, use `python3` for `py`.

The vanilla adapter builds into `oracle/vanilla-adapter/build/<platform>/`, and the runner's logs and reports go to `build/rig/<platform>/`. So one checkout can be run from Windows and from WSL.

### `record`

Starts the vanilla adapter (build it first with `py -I oracle/vanilla-adapter/build.py`), runs every case, and writes:

- `golden/26.3/<probe>.jsonl`: every full result, one per line, with blobs in base64
- `expected/26.3/<probe>.json`: each case's hash, the configuration, and the adapter's `about` (JVM, flags and OS)

Other configurations write into a subfolder named for them, such as `expected/26.3/intrinsics/`.

Quarantined cases get a golden but no hash: they aren't repeatable, so a hash would change on every record.

It reports how many hashes are new, changed and removed, and names the changed cases. For a game update, that list is the behavior change. If any case comes back `error` or `unimplemented`, that probe isn't written at all, since a case vanilla can't run is a broken case.

### `check`: the self-check

Runs vanilla again and compares with its own expected hashes (`P1.3`, `P1.4`). A case that doesn't repeat can't be used to judge Calcite. `--variants` picks what changes between runs:

| Variant | What changes |
| --- | --- |
| `default` | Nothing. Catches anything that depends on time or the process |
| `shuffled` | Case order, so no case depends on the one before |
| `twice` | Every case runs twice in one process, comparing the second, which catches state carried between cases |
| `interpreter` | `-Xint`: no JIT at all |
| `c1` | Only the C1 compiler |
| `c2` | Only C2, compiling early |
| `serial-1cpu` | Serial GC on one CPU |
| `parallel-8cpu` | Parallel GC on eight CPUs |

Generation order isn't a variant, since a case's ops say it: the same chunks decorated in different orders are cases of their own, `cases/features/orders.json`, each giving the world its decorations left (`final`). They repeat like any other case, and Calcite has to match each order. `orders` says which came out the same whatever the order (CAL-33).

With `--quarantine`, the cases that didn't repeat are added to `expected/26.3/quarantine.json`, with what varied. Quarantined cases aren't scored. Quarantine a case only after reading why it varies; if Calcite should do something definite instead, add a [difference](differences/README.md) too.

### `score`

Runs an adapter (`--adapter calcite`, the default, or `vanilla`, or a path to an `adapter.json`) on every case, and prints the scoreboard:

| Outcome | Meaning |
| --- | --- |
| Pass | Same hash as vanilla |
| Fail | A different hash, and no difference covers it |
| Difference | A different hash, covered by an entry in `differences/` |
| Unimplemented | The adapter doesn't have this probe, or this part of it, yet |
| Error | The adapter failed or crashed, or the case's probe version doesn't match |
| Quarantined | Vanilla itself isn't repeatable here, so it isn't run |
| Unrecorded | No expected hash yet. Run `record` |
| Elsewhere | The case is for another system, as its `system` says, so it isn't run here |

The score is passes over the cases that count: everything except differences, quarantined, unrecorded and elsewhere cases. `ping` tests the rig itself, so its row is marked `(rig)` and it isn't part of the total. The full report, with every case's outcome, goes to `build/rig/<platform>/scoreboard-<adapter>.json`. Adapter logs go to `build/rig/<platform>/logs/`.

With `--strict`, it exits with status 1 if any case fails or errors, as CI runs it. Unimplemented cases don't count.

Scoring vanilla against itself should always give 100%. If it doesn't, something isn't repeatable that the self-check missed.

### `diff`

Runs one case on an adapter and compares it with vanilla's golden: the output fields, the blob count, and for each blob the first differing byte, with a hex dump of that row. It needs the goldens from `record`, which are only on the machine that recorded them.

## Case files

Cases live in `cases/<probe>/*.json`. The format is in [`PROTOCOL.md`](PROTOCOL.md#case-files). Hand-written files cover edge cases. Generated ones (`generated.json`, `limits.json`) come from the `gen.py` beside them, which is deterministic: run it again, on any machine and any Python the runner supports, and the file comes out the same. The runner's tests rerun every generator and compare (D249). So nothing a generator writes may depend on the machine: zip files have fixed times and are laid out by the generator, not `zipfile`, which marks each entry with the system it ran on, and every deflate, zlib or gzip stream comes from [`deflate.py`](runner/deflate.py), not Python's `zlib`, which compresses with whichever zlib Python was built with (zlib-ng on Windows from 3.14, classic zlib elsewhere, with different bytes). The generators that name vanilla's data read its ids from the pinned jar, so they need `oracle/fetch.py` run first; the tests skip them without it.

A case whose blobs vanilla doesn't write in the same order every run says `"unordered": true`, and the runner ([`unordered.py`](runner/unordered.py)) sorts each compound in them by key before hashing (D192).

### Blobs in case files

Each entry in a case's `"blobs"` is one part, or a list of parts joined in order. The runner expands them to bytes, so adapters only see bytes.

| Part | Bytes |
| --- | --- |
| `"AAEC"` | Base64 |
| `{"hex": ["00ff", "10 20"]}` | Hex, spaces allowed |
| `{"f64": ["1.5", "-0", "inf", "nan", "0x1p-1074"]}` | `f64`s, big-endian. Decimal or hex-float strings |
| `{"f32": [...]}` | `f32`s, rounded from those values |
| `{"f64_bits": ["7ff8000000000001"]}`, `{"f32_bits": [...]}` | Exact bit patterns in hex, such as NaN payloads |
| `{"i32": [1, -2]}`, `{"i64": ["-9223372036854775808"]}` | Integers, big-endian |
| `{"gen": "f64_bits", "seed": "1", "count": 1000}` | `count` random `f64` bit patterns: every NaN, infinity and subnormal included |
| `{"gen": "f32_bits", ...}` | The same for `f32` |
| `{"gen": "f64_range", "seed": "1", "count": 1000, "min": "-10", "max": "10"}` | `count` values in `[min, max)` |
| `{"gen": "f64_range", ..., "ranges": [["0", "100"], ["-10", "10"]]}` | `count` tuples, one value from each range, for two-argument functions |
| `{"gen": "f32_range", ...}` | The same, rounded to `f32` |
| `{"gen": "i32_range", "seed": "1", "count": 3000, "min": "-30000000", "max": "30000000"}` | `count` integers in `[min, max]` |
| `{"gen": "i32_range", ..., "ranges": [["-64", "64"], ["-64", "320"], ["-64", "64"]]}` | `count` tuples, one integer from each range, such as block positions |

The generators use SplitMix64 from the given seed. A range value is `min + (max - min) * u`, with `u` the top 53 bits of the next output times 2^-53, computed in `f64`. `i32_range` takes the next output modulo the range's size. These definitions are fixed: changing one changes every case that uses it.

## The Calcite adapter

`calcite-adapter/adapter.json` starts [`launch.py`](calcite-adapter/launch.py), which builds [`src/rig/adapter.calx`](../src/rig/adapter.calx) with `calx build --release` and runs it (D87). The build takes under half a second, and about 50 ms when nothing changed, so it happens on every start. The binary goes to `build/rig/<platform>/`.

- calx is found from the `CALX` environment variable, then `PATH`, then `../calx/build/compiler/<platform>/` beside this repository. calx finds clang itself.
- `CALCITE_DEBUG=1` builds the adapter in debug mode, where it checks that it frees everything it allocates and exits with status 102 if not.
- It implements `ping`, `rng`, `collections`, `registries`, `palette`, `chunk`, `region`, `chunk_nbt`, `level_data`, `world_folder`, `allow_list`, `entities_poi`, `tickets`, `ticks`, `levels`, `distance`, `light`, `spawn`, `packs`, `noise`, `density`, `biomes`, `terrain`, `surface`, `carvers`, `math`, `strictmath` and `mth`, which pass 100% on Windows and Linux; `nbt` for binary input, whose 32 cases pass, while its SNBT cases wait for the SNBT parser; `features`, whose 557 cases pass, the seed grid's 60 among them (CAL-84, CAL-85, D267); `structures`, whose 89 cases pass (CAL-85); `datafix`, whose 246 cases of structure templates saved by older games pass (CAL-102, D285); `block_entity`, whose 180 cases of block entities loaded from templates' data pass but for 2 it reports as unimplemented (CAL-92, D286); `environment`, whose 46 cases of the environment attributes pass (CAL-105, D313); and `items`, whose 1155 cases of item stacks read from a data pack's JSON, from SNBT, as a save's are, or from the network, and written to NBT or the network, or hashed as a slot's `HashedStack` is, pass (CAL-77, D362, D363, D364, D365, D373). Each reports a case that reaches a feature, a piece or a structure type it doesn't have as unimplemented. Every other probe reports `unimplemented` until Calcite has the code behind it.
- It runs from the repository's root. `registries`, `chunk`, `chunk_nbt` and `packs` read the vanilla data pack from the pinned jar in `oracle/jars/`, which [`fetch.py`](../oracle/fetch.py) gets.

The adapter's parts are in [`src/`](../src/README.md): the frames in `rig.frame`, their JSON in `json.tree`, and one module per probe.

## Adding a probe

1. Specify it in [`PROTOCOL.md`](PROTOCOL.md#probes), at version 1.
2. Implement it in the vanilla adapter and list it in its `hello`.
3. Add cases under `cases/<probe>/`.
4. `record`, then `check --variants all`. Quarantine what doesn't repeat, and look at why.
5. Commit the cases and `expected/26.3/<probe>.json`.

Calcite's adapter reports the new probe as unimplemented until Calcite can run it. To implement it there, add a module under `src/rig/` and list the probe in `hello` in `src/rig/adapter.calx`.

## Protocol suites

The probes check Calcite's parts. The protocol suites check the server as a client sees it (`P4.8`): the [protocol bot](../src/rig/session.calx), one player made from Calcite's protocol code, runs the same scenarios against vanilla 26.3 and against Calcite, writes down every packet each sends, and the two sessions are compared packet by packet.

```sh
py -I rig/runner/sessions.py                       # every configuration and scenario
py -I rig/runner/sessions.py --config compressed --scenario join
py -I rig/runner/sessions.py --compare-only --show 0
```

[`sessions.py`](runner/sessions.py) builds Calcite and the bot with `calx build --release`, then, for each configuration, starts vanilla in a fresh folder under `build/rig/sessions/CONFIG/vanilla/`, runs the bot once for each scenario, and stops it; then the same for Calcite. Both servers get the same `server.properties`: offline, a flat world named by its seed with no structures, peaceful, a view of 4 chunks, a pause once they've been empty 2 seconds, and the default `white-list=true`, with a `whitelist.json` that lists the bot. The bot runs only once each server has paused, so it joins both at the same game time ([D315](../docs/decisions.md)). Where the bot left by the server's clock, at a game time its steps or `watch` set, which it says, `left at game time`, each server is stopped only once it's paused again, empty 2 seconds by its own ticks, so both run the same ticks after the bot leaves and save the same, however long the stop would have taken to come by the clock; a bot that left by the wall clock, once the server's gone quiet, left at other game times on each anyway, and its server's stopped then and there ([D506](../docs/decisions.md)). The configurations are `compressed`, at the default threshold; `uncompressed`, at `-1`; `inventory`, `join` and `creative` with saved data for the bot, in creative mode with an inventory: stacks in the hotbar, the 27 and the offhand, armor, and components of the kinds the stream codecs send, numbers, enchantments, a name, a potion, a color and one taken away. Both servers send it the same `container_set_content`, byte for byte, and the same equip sound as it puts leggings on, and save it the same, `Inventory`, `equipment`, the slot it holds and its game mode, each compared with its tags' types once the session's done, and its `attributes`, by their IDs, since vanilla saves them from a map that goes by identity hashes ([D375](../docs/decisions.md)); the play packets that differ are Phase 6's recipes, commands and advancements ([D372](../docs/decisions.md)), the player's entity data, health and experience now the same ([D380](../docs/decisions.md)); `clicks`, the bot in survival with that inventory, running the `clicks` scenario: after every click, both servers send it the same packets of the menu, byte for byte, the corrections for a wrong cursor and a stale state, the crafting grid's result and the stacks put back as it closes among them, and the same equip sound as its helmet goes on, and save it the same; the play packets that differ are `inventory`'s, armor's attributes, and vanilla's mobs, which Calcite didn't have yet ([D374](../docs/decisions.md)); it's always taped, `Config.tape`, as the mobs natural spawning puts by the bot are drawn from the levels' randoms, and differed from run to run on both sides ([D548](../docs/decisions.md)), and in it, `inventory` and `compressed` every `update_attributes` is the same from both servers, a new player's, a saved one's, a creative one's and those as a helmet comes off and goes on, and both save the same `attributes` ([D375](../docs/decisions.md)); `dig` and `dig_creative`, on [the dig fixture](#fixture-worlds), with no drops and no natural spawning, and the bot's saved data in survival and creative mode, a wooden shovel held, shears, a golden pickaxe a use from breaking and a sword in the hotbar and torches in its offhand, running `dig` and `dig-creative`: every packet of every step is the same from both servers, spawn protection's message, which an `ops.json` with another player and `spawn-protection=1` give it, the acks, a dig let go too soon and finished on the next tick, aborts, a switch, a stop elsewhere, out of reach, a tripwire cut and the shears damaged, the pickaxe breaking, the hands swapped, and creative's breaks, a bed's head, a door's and tall grass's bottom going with them, a command block refused and a sword that breaks nothing, and both save the bot the same ([D376](../docs/decisions.md)); `saved`, the `join` scenario alone, on a copy of the world [the round trip](#the-round-trip) has vanilla make, so `roundtrip.py` runs first and `sessions.py` skips `saved` with a note until it has; and `terrain`, the same without the world's entities, so the RNG tape shows what its blocks do past the mobs ([D320](../docs/decisions.md)), and without natural spawning, `spawn_mobs` off in the copy's `game_rules.dat`, which both servers read, since vanilla's first mob draws as it spawns where Calcite has no mob ([D338](../docs/decisions.md)). It's at a view of 3, which sends the chunks from -4 to 4, saved full with every chunk around them, and the world's spawn is moved to the origin in both copies' `level.dat`, so the player joins in chunk (0, 0). Vanilla runs from the jar's own classes, which [`build.py`](../oracle/vanilla-adapter/build.py) unpacks, with Mojang's EULA accepted in its scratch folder only; it needs the vanilla adapter built, and never runs in CI. It runs with the rig's [agent](../oracle/vanilla-adapter/README.md#the-agent), which seeds each level's random from 1103 and the dimension's name, as Calcite's `level-random-seed=1103` seeds its own, so what either draws from a level's random, its weather first, is the same on both ([D311](../docs/decisions.md)). Of the packets in play, 522 match, where 74 did, with each chunk's sections compared by what they hold ([D343](../docs/decisions.md)), with block changes compared whatever order vanilla sends their chunks in ([D341](../docs/decisions.md)), and light updates sent to the bot for the chunks on the edge of its view ([D342](../docs/decisions.md)): 130 of vanilla's 136, each section's light the same, a few with a section a step later or sooner, as each server's light runs on a thread of its own; of the rest, most are sand set where it lands, which falls as an entity, and a block set as its chunk was sent, which comes in the chunk on one side and after it on the other. A new player joins at a random place within `respawn_radius` of the spawn, which each server draws its own way, so it's 0 for both: typed into vanilla's console as it starts, and written into Calcite's game rules, `data/minecraft/game_rules.dat`, which it reads as it starts. Each then finds the place itself, on the ground at the spawn, as vanilla's `PlayerSpawnFinder` finds it. `--compare-only` compares what the last run recorded.

With `--trace`, the agent writes the state of each of vanilla's living entities to `entities.txt` in its folder as the level's tick is done with it, `trace=entities.txt`, and a player's as their own tick, `doTick`, is done, before they're put back where their client has them; and Calcite, with `--entity-trace`, its own the same way, a line each: the game time, the entity's ID, its place and motion, its turns, what it's told to walk and its speed, and whether it's on the ground. [`traces.py`](runner/traces.py) lines the two up entity by entity and shows the first tick where they part, each value that differs marked, read as numbers, so Java's `1.0E-4` and Calcite's `0.0001` are the same. A mob's moves are sent to a 4096th of a block, and its motion as rounded, too coarse to find where two servers' mobs part; the trace finds the tick and the value ([D457](../docs/decisions.md)).

The bot cuts its session into steps, `login`, `configuration`, `join`, `walk`, `chat`, `command` and `leave`, and ends a step once the server has sent nothing for a second but its clock and entities' moves, which vanilla's mobs keep sending as long as they wander where Calcite has no mobs yet ([D377](../docs/decisions.md)); `watch` has `login`, `configuration`, `watch` and `leave`, and ends `watch` at the server's time; `creative` has `login`, `configuration`, `join`, `creative` and `leave`; `clicks` has `login`, `configuration`, `join`, a step for each click, and `leave`. The vanilla adapter's [`SessionDump`](../oracle/vanilla-adapter/README.md#reading-sessions) reads both servers' packets with vanilla's own codecs, so the bot's reading agrees with neither server on a mistake, and [`sessiondiff.py`](runner/sessiondiff.py) lines each step's packets up by kind, as `diff` lines up text, a block event or a sound by where it is too, so a piston's run of them, the same two kinds over and over, lines up event by event ([D352](../docs/decisions.md)). Two lined-up packets match when their values are the same tree and their bytes are the same. What depends on timing rather than on the server is taken out first:

- **The clock.** `set_time` and keep-alives come every so many ticks or milliseconds, so each side's are compared once a step, by their values with the times taken out. A keep-alive one server sends a step before or after the other's is lined up with it: they come every 15 seconds from a player's join, which is 300 ticks, so each falls at a step's start, on either side of it on either server ([D572](../docs/decisions.md)).
- **Chunks.** Vanilla sends the chunks that are ready, nearest first, from worker threads, so its batches and their order change from run to run. A step's chunks are compared as a set, by position.
- **Block changes.** Vanilla broadcasts the chunks whose blocks changed in a tick from a `ReferenceOpenHashSet` of their holders, by identity, so in another order between chunks each run, and a light update comes as its light thread gets to the change. A step's `block_update`, `section_blocks_update` and `light_update` packets are compared as a multiset, each of vanilla's matched with one of Calcite's with the same value; those left are paired by where they are, a block, a section or a chunk, to show what differs, and the rest are each side's own, counted by kind ([D341](../docs/decisions.md)). So is the `block_entity_data` that comes with a changed block whose block entity sends its update tag, which comes as the tick it changed in does, between the chunk batches as the change does ([D350](../docs/decisions.md)).
- **Unfixed bytes.** Where vanilla itself writes the same value in other bytes from run to run, only the values must match: tags, `set_time`, and a chunk's heightmaps, which vanilla keeps in a `HashMap` keyed by an enum, so they come out in another order each run. An entity's attributes come from a set of them that goes by their instances' identity hashes, so `update_attributes` is compared with its attributes put in order of their names ([D375](../docs/decisions.md)). A living entity's effects' particles in `set_entity_data` come from its `activeEffects`, a `HashMap` keyed by the effects' holders, which hash by identity, so two or more are compared sorted, as its saved `active_effects` are compared as a set ([D513](../docs/decisions.md)). The recipes' property sets in `update_recipes` are a `HashMap` keyed by `ResourceKey`s, each set `Set.copyOf` of item holders, both of which hash by identity, so vanilla writes them in another order each run; SessionDump puts them in order, and the stonecutter's recipes, a list, keep theirs ([D385](../docs/decisions.md)). The login's levels are `levelKeys()`, put in as `createLevels` goes through the dimensions registry's `entrySet`, a `HashMap`'s by `ResourceKey`, which hashes by identity, so after the Overworld vanilla writes the Nether and the End in either order ([D386](../docs/decisions.md)). An advancement update's `y`, each added advancement's place down its tab, comes of `TreeNodePosition` walking each one's children in the order of a set hashed by identity, so it changes from run to run, and when each criterion was obtained is the server's clock; neither's compared, only whether each criterion was obtained, and the bytes aren't. The advancements it adds, those it removes and those it sends progress of come from a `HashSet` and a `HashMap` filled as that walk goes, whose entries in one bucket keep the order they went in, so each is compared in order of their IDs. An item's enchantments are an `Object2IntOpenHashMap` keyed by their holders, which hash by identity, so two or more are compared in their text's order, and their bytes aren't ([D531](../docs/decisions.md)). The recipe book a player joins with, `sendInitialRecipeBook`, is what they know, a set hashed by identity, so it's compared in order of its displays' numbers, and its bytes aren't. And each session's saved advancements, the bot's `players/advancements/<uuid>.json`, are compared, each advancement with progress in the order it was started, with its criteria obtained in theirs and whether it's done, when each was obtained left out, but for those obtained within a second of each other on both servers, which may swap places once a `reload` has read the files again, as that sorts them by when each was first obtained, to the second ([D572](../docs/decisions.md)); and so is their data's `recipeBook`, its lists sorted, as vanilla's come from sets hashed by identity ([D533](../docs/decisions.md)); and so are the bot's statistics, `players/stats/<uuid>.json`, each type's stats with their counts and in the order they were saved, the types in any order, as vanilla groups them by identity; the times it was in, `play_time`, `total_world_time`, `time_since_death`, `time_since_rest` and `sneak_time`, are told where they differ but don't fail the comparison, as a bot that joins or leaves by the wall clock is in for other ticks on each server ([D542](../docs/decisions.md)).
- **How a section's written.** A chunk packet's sections are compared by what they hold, each one's counts and the state and biome at each place, as the client reads them, not by how their palettes are written: Calcite sends one of 17 to 128 kinds at 8 bits a value where vanilla takes 5 to 7 ([D271](../docs/decisions.md)), and lists a new section's kinds air first where vanilla, reading one back from a region file, lists them in the order they first come. The rig's probes compare `Section.write` with vanilla's byte for byte ([D343](../docs/decisions.md)).
- **The sky under the world.** Vanilla sends the section below the world's bottom with a sky layer of 2048 bytes of 0 for the first chunk whose sections its light sets up in a batch, `repeatFirstLayer`, and empty for the rest, `new DataLayer()`; which is first goes by which of its workers finishes first, so it changes from run to run. A layer under the world that's all 0 is read as empty on both sides, in `emptySkyYMask`, as the client reads both as 0 ([D357](../docs/decisions.md)).
- **Entities.** What an entity other than the bot is sent comes on its own clock, from the tick it came in, as its tracker runs every so many ticks, so a step that ends a second after the bot last heard anything else ends between two of them where the clock has it. Each entity's packets are lined up across the session instead, by its ID ([D390](../docs/decisions.md)): its coming, its data, its going and its pickup in the order it was sent them, which must be the same, and apart from those its moves, in theirs. Two entities that came in different ticks, as the bot's packets fell between the server's ticks, meet, merge or are picked up a tick or two apart on each server, so where its state comes among its moves, and how many moves it's sent before it goes, aren't the server's to fix: one side's moves may go on past the other's by as many as 6, three of an item tracker's runs.
- **What vanilla draws.** The session ID a server draws as it starts, which `login_finished` carries, the time on a chat message without a signature, a sound's seed, which vanilla draws from a random seeded afresh as it starts, and a player's latency, how long their client took to answer a keep-alive, 0 or 1 milliseconds on one machine ([D558](../docs/decisions.md)), are left out of both sides.

Each packet that differs is keyed `session:SCENARIO/STEP/KIND`, such as `session:join/configuration/custom_payload`, which a file in [`differences/`](differences/) can cover, with `*` for any scenario. The status scenario and the login and configuration steps are the suites the Phase 4 gate needs (`G4.2`): `sessions.py` exits with 1 if one of them has a difference no file covers, or if the bot's saved data differs after a configuration that gives it some. Play is reported, not gated, until Calcite sends what vanilla sends there. After a configuration that loads a fixture, what both servers saved of the fixture's chunks, from -1, -1 to 0, 0, is compared by [`savediff.py`](runner/savediff.py) ([D384](../docs/decisions.md)), reported, not gated: each block's state, by its place, not by how its section's palette is written, each block entity by its position, the block and fluid ticks waiting, as sets, the heightmaps and the rest of each chunk's tags, and the light. So are their entity chunks, each chunk's entities by their UUIDs in the order it saved them, and each entity's tags but those that tell when the server stopped, an item's age and its motion ([D391](../docs/decisions.md)). `LastUpdate` and `InhabitedTime` are left out, as the bot's steps land on different game times on the two servers, and so is the section below the world's sky layer of 0s, which vanilla gives some chunks and not others (see "The sky under the world"). After `dig`, `dig_creative`, `place`, `place_creative`, `use`, `use_items`, `use_books`, `use_containers` and `crafts`, every chunk both saved is the same. A run of every scenario also notes a difference file whose session cases covered nothing, as `score` does.

Status, login and configuration pass in every configuration, with the server's [brand](differences/brand.md) the one deliberate difference. Play matches in its positions, where the player spawns among them, its chat, the unknown command's answer and every chunk on the flat world, 166 packets ([D343](../docs/decisions.md)), and differs where Calcite has yet to do what vanilla does, each with the phase that brings it:

- the recipe book's recipes, the command tree and advancements (Phase 6); `update_recipes` is the same since ([D385](../docs/decisions.md)); the player's entity data, health and experience are the same since [D380](../docs/decisions.md)

On the saved world, the two servers read the same chunks and light them the same: 73 of the 81 match byte for byte, light included. A step's chunks that differ are reported as the first, then the rest grouped by the fields they differ in. Six differ only by their block entities (Phase 6). Two hold the round trip's sand and water, whose ticks wait in the save: vanilla runs them as the player joins, so its sand falls and its water spreads, with the light and heightmaps that change with them, where Calcite ticks no blocks yet (Phase 6). Vanilla also sends light updates for the chunks at the edge of what it's lit, which carry the light their chunk packets did, and others with the block changes of water flowing in caves ([D184](../docs/decisions.md)). Its mobs and the round trip's entities keep moving, so its join step never goes quiet and ends at the bot's timeout.

## Fixture worlds

```sh
py -I rig/runner/fixtures.py                          # build each fixture in rig/fixtures/ not built yet
py -I rig/runner/sessions.py --config redstone --tape # build redstone's if it isn't, and watch it run
```

A fixture is a small world vanilla builds from console commands, which a session then has both servers load, so what's built runs the same on each and is compared packet by packet and draw by draw (CAL-116). Its commands are a file in [`fixtures/`](fixtures/), `NAME.txt`, one to a line, with `#` comments. [`fixtures.py`](runner/fixtures.py) starts vanilla on the sessions' flat world, from the same seed, in `build/rig/fixtures/NAME/`, force-loads chunk (0, 0), freezes its ticks with `tick freeze`, so the ticks each block set schedules wait in the save rather than run, and types the commands, `setblock`, `fill`, `setworldspawn`, `summon`, `time` and `forceload`, each answered as it should be or the build stops. Then it lets the chunk go, forces again the chunks the fixture's own `forceload` forced, which the world keeps ([D428](../docs/decisions.md)), saves and stops. The world keeps only its full chunks: vanilla begins those around the forced one and goes on with them where it left them, as Calcite does too ([D334](../docs/decisions.md)), but listing their kinds in another order, so they're taken out of its region files and each server makes them anew. A world built from the same commands, by a hash of them, is kept; `--force` builds it again, and `sessions.py` builds the fixtures its configurations load as it starts ([D344](../docs/decisions.md)).

The `redstone` configuration loads [`redstone.txt`](fixtures/redstone.txt)'s world, by its spawn, in the player's chunk, on a stone floor, so no grass under a block turns to dirt before the reseed, when the two servers' draws differ: two observers watching each other, a clock, each lighting a lamp behind it; one clock's pulses along wire, through a repeater, into a lamp; a torch powering the stone it's on through wire round a corner, off and on every 2 ticks until it burns out, and on again 160 ticks after; and a redstone block powering wire, once, into a repeater of the longest delay, which lights a lamp. Its clocks never stop, so the server never goes quiet for a step to end, and the bot runs `watch`, leaving at the same game time on both, after the same `set_time`, so both sides' sessions hold the same ticks. ## The round trip

```sh
py -I rig/runner/roundtrip.py          # make a world in vanilla, then the round trip
py -I rig/runner/roundtrip.py --reuse  # the round trip on the last run's world
```

A world vanilla made and saved must come back from Calcite as it went, and open in vanilla as its own does (`G5.2`). [`roundtrip.py`](runner/roundtrip.py) runs in `build/rig/roundtrip/`, with Mojang's EULA accepted in its scratch folders only, in four steps:

1. In `vanilla/`, vanilla's server makes a world from the seed `calcite` and loads 64 chunks of the Overworld and 16 each of the Nether and the End, which it generates with the chunks around them, at the statuses they reach. The protocol bot joins, so there's a player's data, advancements and statistics. With the ticks frozen, so that they're saved as they're set, the console then puts in block entities (chests, one holding a written book, a sign, a furnace), points of interest (a bed, a bell, job sites, a beehive and a nether portal), entities (a named pig, a librarian, an armour stand, an item, a minecart with a chest, a zombie with a chicken riding it, a strider and an end crystal), sand and fluids waiting for their ticks, a scoreboard, a team, command storage, a random sequence, a boss bar, the world border, the weather and the time. Then it saves and stops.
2. In `calcite/`, [`src/rig/resave.calx`](../src/rig/resave.calx) loads a copy and saves it again: `level.dat`; every chunk, entity chunk and POI chunk of every dimension, each region's written into its file together; every saved data file, the world's and each dimension's; and the player's data, advancements and statistics. Each goes through Calcite's reader and writer, `storage.chunk`, `storage.entities`, `storage.poi` and the rest, so nothing is copied as it was. A line it logs is a difference.
3. The vanilla adapter's [`WorldCheck`](../oracle/vanilla-adapter/src/calcite/rig/vanilla/WorldCheck.java) reads both worlds with vanilla's own readers and compares them file by file and chunk by chunk, as trees, then as bytes; `LastPlayed`, the region files' timestamps, their sectors and their compressed bytes are left out, and a backup, `level.dat_old` or a player's `.dat_old`, is compared with the file it replaced. Anything that isn't the same, and anything vanilla logs reading Calcite's save, is a difference, up to five a file.
4. In `back/` and `again/`, vanilla's server opens a copy of Calcite's save and one of its own and answers the same 22 questions from its console about each: what the chests, the sign and the furnace hold, in two dimensions, whether the portal and the bed are there, the score, the storage, the border, the forced chunks in each dimension, the teams, the boss bar and each entity. An answer that isn't the same for both, or a warning or error vanilla logs opening Calcite's save and not its own, is a difference. The answers are kept in `answers.json`.

It exits with 1 if there's a difference. It needs the vanilla adapter built, and runs Calcite's release builds of the bot and `resave`; it never runs in CI. It passes on Windows and Linux: 51 files and about 3400 chunks the same, the same in order too, and vanilla answers all 22 questions about Calcite's save as about its own. This is the storage layer: once the server loads and saves a world itself, the round trip goes through the server.

## Worldgen with packs

```sh
py -I rig/runner/terragen.py            # both servers generate the sample, then it's compared
py -I rig/runner/terragen.py --orders   # and vanilla a second time in another order, for scale
py -I rig/runner/terragen.py --reuse    # compare the last run's worlds again
py -I rig/runner/terragen.py --areas 2  # only the first two areas
py -I rig/runner/terragen.py --no-packs # the same without the packs, in build/rig/terragen/plain/
py -I rig/runner/terragen.py --calcite  # Calcite's worlds again, against the last run's vanilla ones
py -I rig/runner/terragen.py --calcite --part-way  # each area's middle first, then the whole
```

The worldgen probes check Calcite's generator piece by piece on vanilla's own data. [`terragen.py`](runner/terragen.py) checks it whole, as the server saves it, on packs that replace most of it: Terralith and Terratonic, the packs of the worldgen benchmark ([`bench/terralith.py`](../bench/terralith.py), which fetches them and checks their SHA-512s), with that benchmark's seed. It runs in `build/rig/terragen/`, with Mojang's EULA accepted in its scratch folder only. Vanilla's server freezes its ticks, force-loads the middle 8 by 8 chunks of six areas of 12 by 12 (the spawn's, the benchmark's measured area's and four far from both), waits until each is loaded, saves and stops. A force-loaded chunk ticks, and vanilla post-processes a chunk as it starts to, so what's compared is the ring 2 out from those, at each area's edge, which they need full and which never tick, as a pregenerated chunk is. Calcite's release build pregenerates the areas and stops. Then each chunk of the rings is read from both worlds' region files and compared.

Where features from neighbouring chunks meet, what comes out depends on the order the chunks were decorated in, which vanilla doesn't fix and Calcite fixes as its own ([D29](../docs/decisions.md), [D214](../docs/decisions.md)), so the comparison is in two parts ([D288](../docs/decisions.md)). What must be the same is each chunk's status, its biomes, its structure references, its starts but for the flags pieces set as they're placed, and the block entities both worlds have, as they're saved, a chest's loot table seed and all; it exits with 1 if any isn't. What the order moves is counted: the blocks, heightmaps, ticks and blocks to update, and which block entities there are. With `--orders`, vanilla makes the sample a second time, force-loading one chunk at a time from the far corner, and what that moves is counted the same way. Every chunk of the sample has what must be vanilla's, with the packs and without. With them, two vanilla runs differ in 17,124 blocks in 194 of the 264 chunks, mostly ore and stone blobs over each other, dripstone and sculk, and Calcite differs from the first in 23,097 in 223, of the same kinds. The mobs each area's chunks spawned as they generated are compared as well, from both worlds' entity files ([D508](../docs/decisions.md)): each as it's saved but for its UUID and a chicken's egg time, which come from a random of its own, seeded from its ID and so from the order vanilla's threads made the chunks in, and with its attributes sorted, which vanilla saves in the order of a hash map keyed by identity. A ring chunk whose heightmaps are vanilla's must have vanilla's mobs, unless vanilla's has a type Calcite doesn't make yet, a structure's or a creature's, which ends the chunk's spawning in Calcite. `--part-way` has Calcite pregenerate each area's middle 10 by 10 first and stop, so the ring is saved lit at `minecraft:light`, its mobs still to spawn, and then the whole, carrying on from what it saved. A shipwreck's height, which it works out from the heights around it the first time it's placed, is counted with what the order moves. Without the packs, vanilla's sample has 147 mobs in 63 chunks and Calcite's 87 in 31, each of those 31 the same as vanilla's, one pass or part-way; the other 32 have a type Calcite doesn't make: mineshafts' chest minecarts, villages' villagers, cats, golems and cushions, rabbits, parrots and a polar bear. With them, 17 chunks are the same and 37 have such a type. Light and the times a chunk keeps aren't compared. Everything is written to `build/rig/terragen/report.json`. The packs are Stardust Labs', so nothing it makes is committed, and it never runs in CI.

## A chunk as it starts to tick

```sh
py -I rig/runner/ticking.py           # both servers load the saved world and send its chunks, then they're compared
py -I rig/runner/ticking.py --reuse   # compare the last recording again
```

Vanilla post-processes a chunk as it starts to tick, `LevelChunk.postProcessGeneration`: each block its generation marked, `PostProcessing`, has its fluid tick at once, a liquid's block its own tick, and any other block is made again from those around it. [`ticking.py`](runner/ticking.py) checks Calcite's against vanilla's on the round trip's world, whose chunks from -6 to 5 are full, and more to the north and east, where vanilla loaded the spawn's: those vanilla ticked it post-processed before it saved them, and those at the edge, that it didn't, still have their marks, aquifers' water and lava, mushrooms, ice, glow lichen and leaves. Round the full chunks the save has a ring with its features, waiting for its light, then one with only its terrain: among the chunks from -8 to 7, at -7 and -8 on the west, 6 and 7 on the south, at the north-west corner, and on the east south of 0. Each server loads a copy, as [`sessions.py`](runner/sessions.py) records a session, and the protocol bot joins at the origin with a view of 10, so the chunks from -8 to 7 are all sent, each server finishing the part-way rings first, from where it saved them: Calcite since [D334](../docs/decisions.md) (CAL-113), and from the start before it ([D333](../docs/decisions.md)). Each chunk packet's blocks are decoded, so how a palette is written ([D271](../docs/decisions.md)) doesn't count, with the blocks each `block_update` and `section_blocks_update` after it sets, as the client keeps them, so what blocks' ticks set after the chunk was sent counts ([D337](../docs/decisions.md)), and those of the 256 chunks from -8 to 7 compared. A block that differs in a way that waits on something not in Calcite yet, or comes of the levels' draws, which part from vanilla's here with no tape to seed them again, is counted under it: precipitation's snow, laid where each server's own draws put it ([D340](../docs/decisions.md)), random ticks, whose draws part from vanilla's while Calcite has few blocks', and falling blocks. Since the blocks set after count, some come of how long each server ran after it sent them, which the probe doesn't line up. Any other is a difference, and it exits with 1. Neither side's packets are dumped to JSON, which for this many block updates runs to gigabytes. It needs the vanilla adapter built and the reports datagen writes, and never runs in CI.

```sh
py -I rig/runner/realclient.py --watch --command "pregen radius 3000" --command "pregen start"     # joining while it pregenerates
py -I rig/runner/realclient.py --fly 25 --seed 114862964781274189     # a flight at 25 times vanilla's flying speed
```

Everything else here plays the client's side with Calcite's own code. [`realclient.py`](runner/realclient.py) runs the game itself instead: Mojang's 26.3 client, from the files of a launcher that has run 26.3 once (the official launcher, the Modrinth App or Prism Launcher), each checked against the SHA-1 in 26.3's version file, with JDK 25 ([D162](../docs/decisions.md)). It starts Calcite's release build, `build/server/calcite.exe`, in a fresh folder under `build/rig/realclient/`, and the client in a game folder beside it, with its sound off and the first-run screens skipped, joining with `--quickPlayMultiplayer`. On Windows, [`realclient_keys.ps1`](runner/realclient_keys.ps1) then plays it a little: the debug screen on, a screenshot, a walk of about 11 blocks and a jump, a screenshot, a chat message and a last screenshot. It sends a key only while the client's window is in front and stops if it isn't, so nothing is typed into another window; it does take the focus for about 10 seconds. It passes if Calcite logs the join and the message, the client gets the message back, nobody is disconnected before the client is stopped, and the client logs no error but the ones on its download threads, which Mojang's services and Realms give a client with no account. The screenshots show the coordinates before and after the walk. It needs a desktop and a launcher's files, so it isn't in CI.

The client's render distance and the server's view distance are both 32, as far as the client lets a player see, so what's measured is what such a player gets; `--view N` sets another.

With `--dimension ID`, such as `the_nether`, Calcite's console then runs `calcite dimension ID` for the player once they've chatted, which takes them where a portal would, onto the nearest place they can stand once it's loaded, with the respawn packet vanilla sends a player whose level changes ([D268](../docs/decisions.md)), and a last screenshot is taken there 8 seconds later with the debug screen on, which names the dimension. It passes if Calcite logs the move and the screenshot's taken.

With `--watch`, the client joins through [`chunkwatch.py`](runner/chunkwatch.py), a relay that passes every byte on as it came and reads the frames each way on the way, the handshake, login, configuration and play, with the compression the server turns on, so it watches Calcite or vanilla alike. For the join and for each dimension the player goes to, it reports the chunks the client was sent, their bytes, the batches, when the last was sent, and when the client had half of them, 90%, 95% and all, by the `chunk_batch_received` it answered each batch with, in `build/rig/realclient/watch.json`, with each batch's time and size and each answer's time and the chunks a tick it asked for. The client answers each batch once, in order, so the nth answer is the nth batch's. `--mbit N` caps what the server sends at `N` megabits a second, and `--ms N` makes each way `N` milliseconds late, so the times are those of a player at the other end of a home link: the bytes go on in pieces of 4 KB, one after another at the rate, each late by the latency however many are on the way, and the report says how long they waited for the link, which anything sent with them, such as another player's move, waited too. `--dump FILE` writes each chunk packet the client was sent to `FILE`, as it was before it was compressed, so compressors can be tried on the chunks a real client got. `--set KEY=VALUE` gives the server a calcite.properties setting, any number of times, and `--command TEXT` types a command into its console once it's ready, before the client starts, such as `pregen start` (CAL-71), any number of times, in order. It reads frames only in offline mode: online, they're encrypted, and it only passes them on. It's how chunk sending is measured ([CAL-99](https://acta.aaenz.no/aaen-studios/calcite#CAL-99)): with the real client, which paces itself as players' do, not the test bot.

With `--fly SPEED`, the client flies instead of walking and chatting, to see whether the chunks keep up with a player who outruns them ([CAL-94](https://acta.aaenz.no/aaen-studios/calcite#CAL-94)). It joins through the relay, as with `--watch`, as an op from ops.json. Once its join's chunks have stopped coming for 3 seconds, and the server's memory has been read as a still player's 15 seconds later, the keys:

1. type `/calcite flyspeed SPEED` in its chat, `SPEED` times vanilla's flying speed, each character as the client's keyboard layout has it;
2. double-jump to fly, and climb for 0.7 seconds;
3. hold W for `--fly-seconds`, 30 unless given;
4. let go, and give the chunks up to 60 seconds to catch up.

The relay also follows the player, from their moves and the server's teleports, and keeps which chunks the client has, each it was sent until it's told to forget it. Four times a second it counts how much of the circle of the view about the player the client has, and how far the nearest chunk it doesn't is. The flight and what follows it are phases of their own, `flight` and `after`. For each, the report gives the speed in blocks a second, the chunks a second the client was sent, the share of its view it had on average and at the least, and the nearest chunk missing. The server's ticks during the flight come from its `--tick-times` file. Everything goes in `build/rig/realclient/flight.json`, with the server's memory. `--seed N` gives the new world that seed, so flights over it compare.

Every run also reports the server's memory, its working set on Windows and resident set on Linux, sampled as it runs:

- before the client joined, which with `--fly` is 15 seconds after the server was ready;
- with the player still, 15 seconds after the join's chunks stopped coming with `--watch` or `--fly`, which is past the 5 seconds after which the server lets go of what making them kept ([D226, D228, D254](../docs/decisions.md));
- the most it had.

With `--world PATH`, the server's world is a copy of the world folder at `PATH`, such as the one the round trip has vanilla save, so the client is sent the chunks it saved, read from its region files, and not the flat world alone.

Without `--online`, the server is offline and the client is `RealClient`, with no account, so its chat isn't signed. With `--online NAME`, the server is in online mode, and the client plays as the Modrinth App's account `NAME`, which must be your own. Its session is renewed as the launcher renews it, from the launcher's Microsoft refresh token through Xbox Live to a Minecraft access token, and kept in memory: no token is printed or written, and nothing is written back to the launcher. The client then fetches its chat key from Mojang and signs what it says, and the message must come through signed on both sides: Calcite logs it without `[Not Secure]`, and so does the client. That is `G4.1`. What the client checks of signed chat, `ChatCheck` also checks after every test run, as vanilla's client checks it (see [the adapter](../oracle/vanilla-adapter/README.md#checking-calcites-packets)).

## Found so far

- **Deep SNBT overflows the stack.** Vanilla's SNBT parser has no depth limit. From about depth 511 it throws `StackOverflowError`, at a depth that changes with case order and JIT tier. Quarantined, and listed as a [difference](differences/snbt-depth.md).
- **Over-long strings depend on where they're written.** A string over 65,535 bytes can't be written in the network form (the packet fails), but the file form quietly writes `""`. The `nbt` probe returns both.
- **`Math` isn't `StrictMath` on x86-64.** HotSpot's intrinsics differ from `StrictMath` by 1 ULP on 3% of `sin` and `cos` results, 9% of `pow`, 7% of `log` on (0, 1), and similar shares of `tan`, `exp`, `log10` and `cbrt`. `tanh` differs by up to 2 ULP. `mathcmp.py` measured this on 500,000 arguments per range, with the same counts on Windows and Linux. It's why the rig records [two configurations](#vanillas-two-configurations). Full table: [`CALX_SPEC.md`](https://github.com/ellipog/calx/blob/main/docs/CALX_SPEC.md#transcendental-functions).
- **With the intrinsics off, `Math` is exactly `StrictMath`, but for a NaN's sign.** Under `-XX:-UseLibmIntrinsic`, every function matched on all 22 million arguments. Calcite's `math` probe then found that `Math.log`, `log10` and `pow` give the NaN `0x7ff8…` where `StrictMath`'s fdlibm gives x86's `0xfff8…`, and that `%` keeps a float NaN's sign in Java but not in Calx. No code sees a NaN's sign, so the math probes compare NaNs as NaNs since v2 (D208), and Calcite passes all 162 cases.
- **Each configuration agrees with itself.** Every case gives the same bits under the interpreter, C1 and C2, in both configurations. So does `Mth`'s sine table: rounding to `f32` hides the 1-ULP differences, and all 65,536 entries equal both `(float) StrictMath.sin` and `(float) Math.sin`.
- **Two float constants in the decompiled source are wrong.** `XoroshiroRandomSource` shows `DOUBLE_UNIT = 1.110223E-16F` and multiplies by that float literal, which would make `nextDouble` inexact. The bytecode holds the double 2^-53 (`1.1102230246251565E-16`), so the decompiler printed a double as a float. Calcite's sources read their constants from `javap`, not the decompiler (D86).
- **Block state IDs are arithmetic.** Each block's states take consecutive IDs, in block registry order, and a state's offset within its block is the mixed-radix number of its property values, with properties in name order and the last changing fastest. The data generator's report lists properties in a different order (its JSON writer puts `type` first), so the [converter](../oracle/datagen/README.md#blocksjson) sorts them itself. All 35,723 states and 1,286 blocks match the `block_state` probe.
- **The block state parser is lenient in places.** It accepts a trailing comma (`oak_stairs[facing=east,]`), a leading zero or plus sign on a number (`note=07`, `note=+7`), and spaces around `=` and `,`. It stops at the first character it can't use, without complaint (`stone trailing` parses as stone). Values are case-sensitive (`TRUE` is rejected), and `Stone` is read as an empty name.
- **The block state NBT reader never fails.** An unknown or malformed block name reads as air, and an unknown property, a value of the wrong type or a value out of range is skipped, leaving the default. 26.3 stores states as `{id, properties}`; the old `{Name, Properties}` form reads as air.
- **Registry IDs and tags come out of the data pack exactly as vanilla builds them.** All 129 `registries` cases match: the 32 synchronized registries' entries in vanilla's order, and the tags of every registry the server sends, 773 in all, with their entries in vanilla's order. Entries of a data-driven registry take IDs in the order of their files' identifiers, which vanilla sorts by path and then namespace, and a tag's tags go in where they're listed, each entry once.
- **Some registry contents come out in a different order each run.** A timeline's tracks, and a dimension type's and a biome's attributes, are filtered with `Map.copyOf`, whose order is seeded at random as the JVM starts, over attributes hashed by identity, so entries that share a bucket of the `CompoundTag` they're written to swap places from one run to the next: `contents-timeline` recorded twice gave two hashes. Those cases compare their compounds sorted by key (D192). A dimension type or biome whose attributes are all ones clients aren't sent still writes `attributes: {}`, since `optionalFieldOf` compares the map with its default before the network codec filters it.
- **Calx's Java-ordered tables iterate exactly as Java's do.** `JavaHashMap`, `LinkedMap`, `SortedMap`, `OpenHashMap`, their sets, `PriorityQueue` and `Deque` give the same results and the same order as `HashMap`, `LinkedHashMap`, `TreeMap`, fastutil's open tables, `PriorityQueue` and `ArrayDeque` in all 420 `collections` cases. Those cases include keys whose hashes all collide, so `HashMap`'s bins turn into trees, fastutil tables that shrink and `trim`, and removal through a priority queue's iterator and fastutil's, where `remove_marked` gives the order fastutil's loop goes over the keys in: 7,698 such loops, 183 of them out of the table's order and 17 halving it (D173).
- **Paletted containers keep what nothing refers to, and the bits nothing uses.** A palette keeps an entry after the last value that was it is overwritten, until the palette is full, and the resize then re-adds only the values that are there, in index order, so the order a client sees depends on the whole history of sets. `pack` re-lists them in the order they first appear, in the bits a palette of that size takes on disk, which is 9 for 300 block states, where memory takes 16. `unpack` keeps a palette's longs as they are, the bits above each long's last value too, and sends them on; past the lists, it turns indices into IDs and those bits go. `fill` spreads a value by doubling, which leaves the low bits of one more copy in those bits. An empty palette, or a value indexing past the palette's end, loads, and fails only when it's read. All 129 `palette` cases match std.palette ([D163](../docs/decisions.md)).
- **Which heightmaps count a block is data in 26.3.** The two `OCEAN_FLOOR` heightmaps and `MOTION_BLOCKING` count the blocks in the tag `blocks_motion_in_heightmap`, and `MOTION_BLOCKING_NO_LEAVES` those in `blocks_motion_in_heightmap_no_leaves`, both of which the data pack builds from `blocks_motion` and `leaves`; the motion ones also count every state with a fluid, and the surface ones every state that isn't air. All 13 `chunk` cases match, from one section high to 254: the heightmaps' longs, the four counts of every section, the sections' bytes and the highest section, through thousands of random sets of 42 states of every kind and then of 600 states at random. Setting a block in the world and in generation aren't the same: `LevelChunk.setBlockState` changes nothing for air (any of the three) into a section of only air, or for the state already there, and keeps four heightmaps, where `ProtoChunk`'s skips only `minecraft:air` and keeps the heightmaps its status names. `primeHeightmaps` passes over `minecraft:air` alone, but cave and void air count in no heightmap, so they make no difference.
- **The whitelist is on by default.** A new 26.3 server has `white-list=true` and an empty `whitelist.json`, so it lets no one in until someone is listed or made an op. The protocol suites' `stranger` found it: Calcite let the stranger in, where vanilla told them `multiplayer.disconnect.not_whitelisted`.
- **Region files come out the same, whole or broken.** All 5 `region` cases match byte for byte, every byte of the files but the clock's times: chunks in the first free sectors that fit, moved past the end when they grow while their old sectors are still taken, cleared, a chunk of 255 sectors kept inside and one of 256 put in a file of its own, every compression with the edges of each format, and 34 broken streams. A damaged header's bad places are dropped as the file opens, but two chunks may still share sectors, and freeing one's frees the other's, so the next write can go over it; Calcite does the same. A file shorter than a sector is padded when it's closed, even if nothing was written. Vanilla prints a chunk's position as `[3, 4]`, and its line for an oversized chunk says `(1048581 bytes} to external file`, with the brace.
- **`level.dat` reads anything and logs nothing.** All 128 `level_data` cases match. A field that's missing or of the wrong type takes its default, and one made of several, the difficulty settings, the spawn or the data packs, takes its default as a whole if any part is wrong: a yaw past 180, a position of two ints, a difficulty given by number. Numbers are read as Java's `Number` gives them, so a double of game time is cut toward zero and clamped, a position may be a list, a byte array or a long array, and `0.5f` is true. Brands keep their first order, each once, removed features and feature flags are written in the order of Java's `HashSet`, and the data packs are written only when they were read, even when they're the default, since vanilla's default is one object and a read one isn't it. Whatever 26.3 doesn't read, such as an old world's weather and game rules, is dropped, and `version`, `Version` and `DataVersion` are written as 26.3's.
- **A world folder keeps going when its files don't.** All 229 `world_folder` cases match on Linux, and the 195 that make no symbolic links on Windows. `session.lock` is written with `☃` at its start and the rest of the file kept. A `level.dat` that can't be read is replaced by `level.dat_old` and kept as `level.dat_corrupted_` and the time, and the server stops only when neither reads. Java's gzip reader checks a member's length and CRC-32 only when a read reaches past its end, and vanilla stops reading at the NBT's end, so a `level.dat` cut off in its trailer, with a wrong checksum or length, or with anything after it reads, while a wrong checksum on a first member the NBT runs past doesn't; a header's CRC is checked, and its reserved flags aren't. A `Data` that isn't a compound, or isn't there, reads as empty, and a root that isn't a compound fails. A `level.dat` that's a folder reads as broken, is moved aside as one, and then fails the check that it's a file, so vanilla tries 10 times to move the file it already moved, logging each, gives up and goes on with `level.dat_old`, leaving neither. `version` is read as `Number.intValue`, so a long or a double of 19133 opens and a string doesn't, and `Unknown data version` gives it in hex, `fffffffb` for -5. A `Series` that isn't a string counts as `main`, and an older `DataVersion` passes the check, for the data fixer to upgrade. A player's `.dat` that can't be read is copied aside as `<uuid>_corrupted_` and the time, and left where it is, and their `.dat_old` read instead; one that isn't a file is passed over without a line, and a player whose files can't be read starts afresh. Player data has no quota but still the depth limit of 512. Saved data, such as `data/minecraft/weather.dat`, is read gzipped if its first two bytes are gzip's and plain if not, with no quota, and anything after its NBT ignored; one that can't be read, an empty file, one whose root isn't a compound and a folder in its place each log `Error loading saved data: SavedDataType[<id>]` and start afresh, and a file with no `data` gives nothing to the type's codec. It's saved gzipped straight over the file, not through a new one, with its folders made; a folder where the file goes or a file where a folder does logs `Could not save data to <name>.dat`. An ID whose `..` leaves the `data` folder fails to read with the same line, and saving it throws out of the save, `IllegalStateException`. A player's advancements and statistics are read through a buffered UTF-8 reader with Gson's strict parser, so bytes that aren't UTF-8 are met only if the parser reads that far before a fault in the text: a document that ends well, then 9000 spaces and a bad byte, fails as unreadable, and one with a syntax error first as not JSON. Advancements log those two apart, `Couldn't access` and `Couldn't parse`, and statistics log both as `Couldn't parse statistics file`. An empty file, or one of only white space, reads as `null`; a byte order mark is skipped; and nesting deeper than 255 and a number of 1024 digits or more are refused. A `DataVersion` that's a number is read as `LazilyParsedNumber.intValue` reads it, so `5023.9` and `4294972319` are 5023, and `1e10000` throws out of the codec, which vanilla doesn't catch; one that's `true`, a string or anything else is 1343. Both are saved pretty, with Gson's HTML escapes, `null` members left out, `DataVersion` where an advancements file already has one and last otherwise, and their folders made; a folder or file in the way logs `Couldn't save player advancements to` or `Couldn't save stats to`. Statistics kept under a player's name are moved to their UUID's file only if the name is all lowercase letters, digits and `-._`, and only if their UUID's isn't there.
- **A symbolic link in a world refuses it, unless `allowed_symlinks.txt` allows where it leads.** All 379 `allow_list` cases match on Linux and all 381 on Windows, each with paths as that system writes them, and the `world_folder` cases with links on Linux. Without the file no link is allowed, and a world with one fails to open with `ContentValidationException: Failed to validate '<world>'. Found forbidden symlinks: <link>-><target>`, each link it found. The file's blank lines and lines starting with `#` are skipped, and each other line is `[prefix]`, `[glob]` or `[regex]`, lowercase, then its pattern, or a prefix if it doesn't start with `[`, even after a space. A `[` with no `]`, a type that isn't one of the three, or bytes that aren't UTF-8 log `Failed to parse allowed_symlinks.txt, disallowing all symbolic links`, and then no link is allowed. Globs and regular expressions are compiled only when the first link is checked, so one that doesn't compile changes nothing in a world without links, and in one with any logs `Failed to compile file pattern list` and refuses them all. A target is matched as the link holds it, neither resolved nor normalized: `../elsewhere` is allowed by `[prefix]..` and not by the server's folder, and `<folder>./x/../elsewhere` by a glob of two names. Globs and regular expressions match the whole target, without regard to case on Windows, and a prefix is plain text, so `[prefix]/srv` allows `/srvx`. A link's own folder isn't walked into, even when it's allowed. A world that's a link is allowed itself, and the folder it leads to is walked, as the link holds it, so a link to the server's own folder finds itself there; a world that's a link to a file fails as `FileAlreadyExistsException` naming the file, since its folder is made where it really is.
- **Entity and POI chunks read whatever they can, and say what they couldn't.** All 147 `entities_poi` cases match on Windows and Linux. An entity chunk's `Position` is read with `ChunkPos.CODEC`, so a list or array of three or more numbers reads its first two, with an error that it isn't a list of 2 ints, and one of fewer is no position at all, which warns `Failed to parse chunk [x, z] position info`; one elsewhere logs that the chunk file is in the wrong location, and the chunk is read anyway. Its `Entities` are read through a `ProblemReporter`, which keeps each problem once in the order it came and logs them all at the end as one warning, `Serialization errors:` and a tree of where each was met, `chunk@[x, z]` at its root: an element that isn't a compound is left out and reported with its index, and an `Entities` that isn't a list is reported once. An empty compound is read with no reporter of its own. A chunk with no entities isn't saved, and one with any is saved with `DataVersion`, `Entities` and `Position`, in that order. A POI chunk's sections are read one by one, and one that can't be read is logged and left out while the rest are kept; a `Sections` that isn't a compound reads as no sections, without a line. `Valid` is any number, true unless 0, and anything else is false; each record's errors are joined newest first, so a section with several bad records logs one line for them all. A record's type is read by name, with `minecraft:` for one without a namespace, and an unknown or malformed one fails the record; `free_tickets` that isn't a number is kept at 0 with an error. Two records at the same place keep the first unless their types differ, when the later one takes its place with `POI data mismatch`. A section's records are saved in the order fastutil's `Short2ObjectOpenHashMap` keeps them: the section's first block first, then by slot, which a mix of the block's place in the section decides. An empty `poi` file reads as a chunk of empty sections, saved as an empty `Sections`.
- **Chunk tickets tell the trackers in vanilla's order, which a table's order decides.** All 274 `tickets` cases match on Windows and Linux: every call to the two trackers, in its order, each table's order and every byte saved. A ticket added where it lowers a chunk's level tells the simulation tracker first, if its type simulates, then the loading tracker, if it loads; one taken out tells the same two, in the same order, of the chunk's new levels. Stale tickets run down and tickets deactivated as the server stops tell the loading tracker first, then the simulation tracker, chunk by chunk in the order fastutil's iterator meets them, which leaves the table's order where a chunk's last ticket goes and its key is taken out ([D173](../docs/decisions.md)). A purge always leaves the tickets dirty. A saved ticket's compound gets its fields before `chunk_pos`, as `mapPair` puts them in, so `ticks_left`, in `chunk_pos`'s bucket, is written first where it's there. Saved tickets are read deactivated, and an optional field that can't be read keeps its default, with its error: a `tickets` that isn't a list reads as no tickets and a `ticks_left` that isn't a number as 0, while a ticket whose type or level can't be read is left out. A negative level can't be saved, since the codec throws, but no ticket vanilla makes has one.
- **Chunk levels settle in vanilla's order, quirks and all.** All 270 `levels` cases match on Windows and Linux: every level the graph sets, in its order, what it has left to do and the levels in their table's order, as the loading, simulation, natural spawn and player ticket trackers have them and with levels, counts and sources at random. A chunk settles a level at a time, lowest first, each level's queue in the order chunks joined it, and its neighbours are checked `x` first, from the lowest, then `z`, wrapping at the ends of an `int`. The chunk vanilla takes as the source, at 1875066, 1875066, never gets a level, and a chunk next to it reads its own source there. If a queued chunk's level changes behind the graph, as a chunk holder's removal changes the loading tracker's, the chunk can be left in two queues; once the second is reached it has no level to work out, which vanilla reads as 255, so it sets itself to the top level and queues itself again on every run, forever. Calcite does the same (one `desync` case sets one chunk 4,000 times in a run), and `world.distance` has to keep the loading tracker's levels from changing that way, as vanilla's own callers do.
- **Scheduled ticks run in vanilla's order, ties between chunks too.** All 190 `ticks` cases match on Windows: every tick each game tick runs, in its order, each chunk's queue in its array's order, the table of when each chunk's first tick is due in its order, and each chunk's ticks as they're saved. A chunk's ticks go by time, then priority, then the order they were scheduled in, and those it was saved with wait, as they were saved, until it ticks, when they're scheduled from the game time then, ordered -n up for its n ticks, so two chunks' first saved ticks can tie. Chunks whose first ticks are due go into a queue by those ticks' priority and order, in the order fastutil's iterator takes them out of the table of when each is due, which isn't the table's order once a run of keys wraps past its end; Java's queue breaks ties by where they went in, and a build that queued them in the table's order fails 3 of the `crowded` cases. A chunk gives its ticks until its next comes after the next chunk's first, and once the limit's reached the chunks left in the queue are told when their next is due, in the queue's order ([D322](../docs/decisions.md)).
- **A player's chunks get their tickets as vanilla's dispatcher lets them, races and all.** All 102 `distance` cases match on Windows and Linux: every holder, ticket, queue and tracker level in its table's order, with players joining, leaving and walking, tickets, distances changing and holders dropping and unloading, and the dispatcher's jobs and the main thread's tasks run in random interleavings. A player's chunks get their tickets nearest first, four at a time, each keeping its place until its chunk ticks its entities, and the dispatcher waits on a holder only from the first update after its ticket in which no holder's level changed. Vanilla's debug status lists the chunks in execution through a stream, whose fastutil spliterator goes over the table from the front where its iterator goes from the back, so chunk 0, 0, the table's null key, comes first either way and the rest come the other way round. A chunk that leaves the view and comes back before the worker has run the job that moves its tasks keeps its old level in `queueLevels`, so the player ticket tracker sees no change, and the chunk gets no ticket until its distance changes again: cases that walk with the worker idle leave chunks in view without their tickets, in vanilla as in Calcite. Vanilla's worker runs its jobs within moments, which keeps that rare, and Calcite's server is to run them right after each update. Vanilla updates the holders whose level changed in the order of a set of their identities, which is different every run, so the vanilla adapter keeps them in a `LinkedHashSet`, and Calcite updates them in the order their levels changed ([D177](../docs/decisions.md)).
- **Light is read as the last run left it, and a section can share its layer with the queue.** All 34 `light` cases match on Windows and Linux: every layer's kind and bytes, as a chunk packet sends them, and the light at blocks at random, block light and sky light, with chunks made, lit, edited, emptied, dropped and loaded again with their light queued, in the overworld, the Nether and dimensions from one section high to 254.
